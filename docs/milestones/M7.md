## M7-A — Paid Operation Admission & Replay

The canonical starting HEAD/origin main is
`c9a107523ce6b5f7c48c6eff02a4268d42245add`, clean and ahead 0 / behind 0.
No live provider, OAuth, remote migration or push is part of this implementation.

### Submission and execution authority

Strict answer requests contain intended `turn`, UUID `submissionId` and `thought`.
The payload identity is lowercase SHA-256 of UTF-8 `JSON.stringify([turn,thought])`,
without trimming or Unicode normalization. Ownership is checked before replay.
Same identity/payload returns current canonical state with no provider admission;
changed payload conflicts. An occupied turn with another identity conflicts and
cannot be reinterpreted as the next turn. The client retains its pending identity
through a network failure; an accepted paused/evaluating answer suppresses new input.

One session-locked transaction accepts the answer, creates its JUDGE operation,
admits round 0 / attempt 1 and advances gameplay into EVALUATING. Only its new
execution owner invokes Judge. The existing adapter's second attempt requires a
separate committed admission; admission/control failures cannot trigger retry.
SDK retries remain zero. Lock order is session -> operation -> run.

Both legacy and adaptive failures preserve the answer and pause ERROR_RECOVERABLE.
Ordinary answer POST is never recovery. Explicit resume of the accepted submission
and expected version opens at most one manual round (recovery_count 0 -> 1).
Each round permits at most two attempts: maximum four admissions per answer,
eight for a two-turn session. A failed recovery is RECOVERY_EXHAUSTED, not rescue,
automatic Reveal or an unbounded retry loop. Successful content policy is unchanged.

### Crash fencing and settlement

The 21-minute round lease exceeds two SDK-default ten-minute attempts plus
scheduling headroom. Every admitted attempt is consumed even if its execution is
ambiguous. Observable transport ambiguity is UNKNOWN; expired ADMITTED runs are
lazily UNKNOWN on explicit resume. Expiry does not refund admission or reopen
execution automatically. Old owners cannot retry or apply gameplay after lease
expiry/newer recovery. No worker, result ledger, outbox or financial reconciliation
is introduced. Existing bounded in-round adapter attempts remain distinct from
blind recall/reopening an abandoned operation.

Validated verdict application, discoveries, guidance, session CAS, run SUCCEEDED
and operation COMPLETED use one PostgreSQL transaction. Failure rolls all semantic
success back; the answer/admission survive for explicit recovery. A response lost
after commit is handled by current-state replay without a new provider request.

### Schema and security

Forward migration `202609130004_m7_paid_operations.sql` adds nullable submission
identity/hash to user_answers, minimal ai_operations, and admission/round/status/
timestamps to ai_runs. Partial uniqueness protects submission and round/attempt
identity; existing session/turn uniqueness remains. Historical answer/run fields
stay NULL, with no invented UUIDs, operations or destructive backfill. Completed
historical gameplay and Final Synthesis telemetry remain readable; the new resume
contract requires a real accepted submission identity, not historical guessing.

ai_operations has RLS ON and explicit PUBLIC/anon/authenticated privileges denied.
The audited postgres server path remains usable. Prior migrations and all Final
Synthesis/content/prompt assets are unchanged.

### Data Retention / Deletion Semantics

Operation-linked answers/sessions cannot be accidentally cascade-hard-deleted:
the operation FK preserves submission -> answer -> operation -> run provenance.
The obsolete production Judge failure rollback no longer deletes accepted answers.
No active non-Judge product deletion feature is changed. Explicit test cleanup
deletes dependencies in order rather than weakening production integrity.

Raw answer text remains nullable/purgeable separately; submission hash and provenance
survive purge. This is implicit hard-delete prevention, not eternal raw-text storage.
M8 retention and explicit account/legal/full-session deletion or anonymization
workflows are deferred and must define ordered handling of dependencies.
