## M6-A — Identity Foundation + Single-Session Claim

Provider-neutral `Account` contains only internal UUID `id`, unique bounded
`externalSubject` (1–255 UTF-16 code units, not whitespace-only, no NUL), and
`createdAt`/`updatedAt`. Subjects are exact identifiers, not trimmed, inferred or
case-folded. No passwords, email, name, avatar or vendor-specific identity.

`AccountStorePort` is a narrow additional primary-persistence capability implemented
by `PostgresPrimaryStore`; the existing anonymous `PrimaryStorePort` is unchanged.
Atomic subject INSERT with conflict/no-op and exact-subject SELECT resolves one
stable account. Resolution replay changes neither identity nor timestamps.

The service-only `resolveAuthenticatedAccount` and `claimCurrentOfficialSession`
application boundary requires a trusted caller to supply the authenticated Account
and explicit current session/device UUIDs. M6-A does not implement login or prove
authentication. No HTTP route accepts client account IDs or arbitrary subjects as
authentication. Trusted upstream auth context and its vendor-neutral subject
namespace are M6-B responsibilities; no auth vendor is selected here.

### Exact-session claim

1. Check that the supplied account exists, holding a key-share lock.
2. Read/lock only `play_sessions.id = supplied sessionId` with FOR UPDATE.
3. Require original anonymous device match and OFFICIAL attempt type.
4. Reject an existing different account owner; never transfer ownership.
5. Same-account replay returns ALREADY_CLAIMED_BY_ACCOUNT without UPDATE.
6. First claim updates only that ID with account ID and injected ClockPort instant
   and returns typed ownership data without changing gameplay state_version.

Typed results: CLAIMED, ALREADY_CLAIMED_BY_ACCOUNT, ACCOUNT_NOT_FOUND,
SESSION_NOT_FOUND, NOT_CURRENT_DEVICE_SESSION, NOT_OFFICIAL,
OWNED_BY_ANOTHER_ACCOUNT. Status is not an eligibility filter: in-progress,
evaluating, recoverable, Reveal-ready and revealed official sessions are eligible.

No history enumeration, most-recent query, date guessing, cookie-history search,
historical auto-merge or account/Daily dedup policy is introduced. Older/newer
same-device sessions stay unclaimed. Anonymous provenance remains non-null and
existing anonymous ownership authorization continues unchanged. Account fields
load internally but do not enter public Play/Reveal projections. Claim leaves
gameplay state_version unchanged so an in-flight Judge reservation remains valid;
normal gameplay updates do not overwrite the account columns.

play and builds available. OAuth start/logout require matching Origin; arbitrary
returnTo values are rejected. Callback origin is fixed server configuration, not
Host/x-forwarded-host or user input. Redirect responses are private/no-store.

POST /auth/google reads the trusted anonymous device, validates only the supplied
OFFICIAL session ID, and starts Google OAuth with fixed /auth/callback redirect.
It sets at most one signed pending-claim cookie (ID + expiry, no Account identity),
HttpOnly, SameSite=Lax, Path=/, Secure for HTTPS, Max-Age=600 seconds. HMAC prevents
client mutation and expiry is checked server-side. PKCE uses the official SSR flow.

GET /auth/callback exchanges code, verifies claims, resolves Account and claims
only that pending session against the current device through M6-A. Every handling
path clears pending intent. Missing/stale/tampered intent means zero claims and
no historical fallback. Pending claims require successful code exchange; a
consumed-code revisit without pending intent may keep a verified existing login
but cannot mutate ownership. Account/claim replay preserves original timestamps.
Login success with claim conflict returns claim_not_applied without account-ID
leak, ownership transfer, fallback claim or automatic signout. Logout clears local
Supabase login but retains anonymous provenance and existing claimed ownership.

### Principal state and route contract

NO_DEVICE / ACTIVE_ANONYMOUS_DEVICE / STALE_ANONYMOUS_DEVICE describe browser
provenance. AUTHENTICATED_ACCOUNT is a separate verified identity, not a replacement
for anonymous provenance. Login may claim only the explicit current OFFICIAL session.

- NO_DEVICE -> explicit POST /api/play-sessions -> ACTIVE_ANONYMOUS_DEVICE.
- STALE_ANONYMOUS_DEVICE -> existing-session operation -> no recovery/replacement.
- STALE_ANONYMOUS_DEVICE -> explicit new-session POST -> new ACTIVE device.
- ACTIVE_ANONYMOUS_DEVICE -> verified login + exact eligible claim -> account owner
  attached to that one session; anonymous provenance and historical sessions remain.

resolveExistingDevice/resolveCurrentDevice return ACTIVE, MISSING or STALE using
only findActiveDevice; no INSERT, touch or cookie write. Lookup errors remain errors.
currentDevice is now resolve-only authorization convenience (undefined without proof).
ensureDevice/ensureCurrentDevice may create/touch/issue cookie only at new-session
POST. GET /api/daily needs no identity for its public content projection, so it no
longer creates/touches a device; normal gameplay obtains identity on explicit POST.

All known-session reads/writes (get, answers, lock, recovery, evaluation-resume,
Reveal GET/POST and legacy Final Synthesis submit/retry/skip) resolve only and stop
before session access without ACTIVE proof. Public SESSION_NOT_FOUND/404 remains
anti-enumerating; internal resolver retains MISSING vs STALE. No new public error
exposes arbitrary session existence. No ownership/history fallback.

Google start resolves only when explicit intent exists and safely rejects missing
proof before OAuth start. Callback exchanges/verifies auth as before; missing/stale
device permits verified login with claim_not_applied and zero claims. Auth status
resolves device only for explicit session checks and never creates anonymous identity.
Account resolution remains the existing auth responsibility; it is not history merge.

### AUTH_COOKIE_SECRET operational contract

Server-only, explicitly supplied for configured auth, minimum 32 characters; never
auto-generated at boot. Keep stable across process restarts and deployments while
pending claims exist (600 seconds), and identical across instances serving callbacks.
Changing it can invalidate an issued pending-claim HMAC: Google login may still
succeed with zero session claims. This does NOT invalidate g1_device. Runtime cannot
prove future deployment stability; deployment operators own secret persistence.
No rotation infrastructure or new credential values are introduced.
