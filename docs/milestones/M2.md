# M2 acceptance — Persistent Daily and four-layer content

## Implementation

M2 replaces the temporary M1 browser/in-memory authority with one PostgreSQL-backed Daily stack. The canonical flow is approved JSON → Zod validation and canonical SHA-256 → idempotent database seed → server-clock Daily → anonymous device → unique Official session → transactional answers/state → Lock → version-bound Reveal → durable resume.

No M3 or later feature was introduced. FakeJudge remains deterministic and provider calls remain zero.

## Database architecture and migrations

The concrete adapter is `postgres.js` in `src/adapters/postgres-primary-store`. No database library enters domain/application code. `supabase/migrations/202609080001_m2_daily.sql` creates the full M2 subset: `content_items`, immutable `content_versions`, `daily_schedule`, `anonymous_devices`, `play_sessions`, `user_answers`, `node_discoveries`, `guidance_events`, and `daily_completions`.

Important database invariants include unique canonical dates and explicit sequence numbers; partial unique `(anonymous_device_id, daily_id)` for Official attempts; unique completion per session; nullable purge-ready answer text; evidence coordinates referencing answers; and nonnegative optimistic `state_version`. A second migration adds a trigger that rejects UPDATE/DELETE of approved content versions. State-changing adapter methods lock/check the current version and atomically persist the answer, structured discovery, guidance, and session transition.

Fresh setup:

```text
pnpm db:migrate
pnpm content:seed
```

Both operations are ordered and rerunnable. CI supplies PostgreSQL 16 and runs migration and seed before checks.

## Approved content

`content/approved/conway-law.v1.json` is the single approved M2 fixture. It contains exactly PUBLIC_PLAY, JUDGE_RUBRIC, SERVER_POLICY, and REVEAL_CONTENT plus version/approval/schedule metadata. `pnpm content:validate` rejects missing layers, invalid versions, empty prompts, duplicate/unknown nodes, invalid turns/thresholds, missing Reveal identity, and Reveal identity inside JUDGE_RUBRIC.

The seed hashes a recursively key-sorted canonical representation. An existing approved version with different content fails with an instruction to create a new version. Only the explicit approved directory is scanned.

## Daily, identity, and ownership

`ClockPort.now()` supplies the authoritative instant. PostgreSQL resolves the latest released schedule; release timestamps are constrained to KST midnight for the canonical date. Tests pin 2026-09-08 23:59:59 KST to Sep 8 and 2026-09-09 00:00:00 KST to Sep 9. Old sessions retain their original `daily_id` and `content_version_id` and remain playable after rollover. A browser-clock override cannot change `/api/daily`.

The server issues a 256-bit random Base64URL token in `g1_device` with HttpOnly, SameSite=Lax, Path=/, one-year lifetime, and Secure when `APP_ENV=production`. PostgreSQL stores only SHA-256. Missing, malformed/unknown, or revoked identities cannot inherit another device; a fresh identity is created. There is no fingerprinting or Auth.

Every session operation scopes lookup/mutation by both session ID and current device ID. Sequential and concurrent starts converge through the PostgreSQL partial unique index. A different device or next Daily receives a different Official session.

## Persistence and public isolation

Submitted thoughts persist only in `user_answers.text`; structured rows retain answer IDs and literal spans, never copied text. Reload and a newly constructed adapter recover answers, discovery, guidance, turn/stage/status, content binding, and state version. Local storage is no longer read or written for game recovery.

Pre-Lock DTOs expose only public Daily data, lifecycle, the device's own thoughts, delivered guidance, and turn information. Rubric, policy, node verdicts, aliases, and Reveal content remain server-side. Reveal GET requires LOCKED/REVEALED ownership and reads the session's bound content version. Reveal POST creates exactly one completion and cannot be bypassed by direct Result navigation.

## Genericization

`ConwayNodeId`, `CONWAY_NODE_IDS`, global max turns, hardcoded required nodes, and hardcoded guidance were removed from generic session/policy contracts. Node IDs come from the validated rubric; thresholds, blocking nodes, max turns, and copy come from SERVER_POLICY. FakeJudge is fixture-aware only through a rubric discriminator and does not own policy or Reveal.

## M3 handoff and limitations

M2 intentionally schedules only the two acceptance-boundary dates carried by the first approved fixture; adding future approved schedules is an editorial seed change, not row-count calculation. Replay UX, accounts/merge, Redis/idempotency/nonce, abuse controls, analytics, adaptive targeting, AI comparison, CMS, and real Judge providers remain future milestones. The FakeJudge recognizes only the approved M2 discriminator.
