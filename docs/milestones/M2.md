# M2 acceptance — Persistent Daily and four-layer content

## Implementation

M2 replaces the temporary M1 browser/in-memory authority with one PostgreSQL-backed Daily stack. The canonical flow is approved JSON → Zod validation and canonical SHA-256 → idempotent database seed → server-clock Daily → anonymous device → unique Official session → transactional answers/state → Lock → version-bound Reveal → durable resume.

No M3 or later feature was introduced. FakeJudge remains deterministic and provider calls remain zero.

## Database architecture and migrations

The concrete adapter is `postgres.js` in `src/adapters/postgres-primary-store`. No database library enters domain/application code. `supabase/migrations/202609080001_m2_daily.sql` creates the full M2 subset: `content_items`, immutable `content_versions`, `daily_schedule`, `anonymous_devices`, `play_sessions`, `user_answers`, `node_discoveries`, `guidance_events`, and `daily_completions`.

Important database invariants include unique canonical dates and explicit sequence numbers; partial unique `(anonymous_device_id, daily_id)` for Official attempts; unique completion per session; nullable purge-ready answer text; evidence coordinates referencing answers; and nonnegative optimistic `state_version`. A second migration adds a trigger that rejects UPDATE/DELETE of approved content versions. Corrective migrations add hash-v2 compatibility and composite relational constraints. State-changing adapter methods lock/check the current version and atomically persist the answer, structured discovery, guidance, and session transition.

Fresh setup:

```text
pnpm db:migrate
pnpm content:seed
```

Both operations are ordered and rerunnable. CI supplies PostgreSQL 16 and runs migration followed by the seed twice before checks.

## Approved content

`content/approved/conway-law.v1.json` is the single approved M2 fixture. It contains exactly PUBLIC_PLAY, JUDGE_RUBRIC, SERVER_POLICY, and REVEAL_CONTENT plus immutable version/approval metadata. Editorial assignments are separately validated from `content/schedule/daily.v1.json`. Adding a future Daily that references Conway v1 therefore neither changes its hash nor requires Conway v2.

The seed hashes a recursively key-sorted canonical representation of the approved content definition only. Hash v2 is `23b30fd0a3cc2fb937c68c0fd09dde220f3e29e08e913fb411f56cc0a86f67e8`. Migration `202609080003_content_hash_v2.sql` recognizes only the known legacy Conway hash (or the already-correct v2 hash), temporarily suspends the approved-row trigger, translates the hash, records `content_hash_version=2`, and restores immutability. Unknown existing Conway hashes abort migration.

Schedule seeding is a no-op only when canonical date, sequence, release instant, and content version all match. Incompatible same-date assignments and sequence collisions fail clearly. Four-layer changes under an existing version still fail and require a new version.

## Daily, identity, and ownership

`ClockPort.now()` supplies the authoritative instant. PostgreSQL requires `daily_schedule.canonical_date = (instant AT TIME ZONE 'Asia/Seoul')::date` and `release_at <= instant`; it never falls back to the latest older row. Tests pin 2026-09-08 23:59:59 KST to Sep 8, 2026-09-09 00:00:00 KST to Sep 9, and an unscheduled Sep 10 to no current Daily. Old sessions retain their original `daily_id` and `content_version_id` and remain playable by ID on an unscheduled later date. A browser-clock override cannot change `/api/daily`.

The server issues a 256-bit random Base64URL token in `g1_device` with HttpOnly, SameSite=Lax, Path=/, one-year lifetime, and Secure when `APP_ENV=production`. PostgreSQL stores only SHA-256. Missing, malformed/unknown, or revoked identities cannot inherit another device; a fresh identity is created. There is no fingerprinting or Auth.

Every session operation scopes lookup/mutation by both session ID and current device ID. Sequential and concurrent starts converge through the PostgreSQL partial unique index. A different device or next Daily receives a different Official session.

## Persistence and public isolation

Submitted thoughts persist only in `user_answers.text`; structured rows retain answer IDs and literal spans, never copied text. `char_count` means PostgreSQL `char_length(text)` and is calculated by PostgreSQL, so non-BMP characters such as emoji count once while raw input is preserved byte-for-byte with no normalization. The API/UI UTF-16 limit remains conservatively safe at 2,000. Reload and a newly constructed adapter recover answers, discovery, guidance, turn/stage/status, content binding, and state version. Local storage is no longer read or written for game recovery.

Pre-Lock DTOs expose only public Daily data, lifecycle, the device's own thoughts, delivered guidance, and turn information. Rubric, policy, node verdicts, aliases, and Reveal content remain server-side. Reveal GET requires LOCKED/REVEALED ownership and reads the session's bound content version. Reveal POST creates exactly one completion and cannot be bypassed by direct Result navigation.

Leak validation is content-derived rather than Conway-specific. Theory, person, year, and optional recognition aliases are extracted from each content definition and forbidden from PUBLIC_PLAY and JUDGE_RUBRIC. A second synthetic non-Conway fixture proves the validator catches every identity category. Recognition behavior remains inactive.

## Foundation integrity closure

The repository audit findings are closed as follows:

- Daily lookup now requires the authoritative KST canonical date and release instant; no schedule means no Daily.
- Editorial schedules are separate from immutable content and excluded from content hashes.
- Seed reruns require exact schedule compatibility and reject date or sequence conflicts.
- Secret validation derives forbidden values from each content definition.
- PostgreSQL calculates Unicode-safe `char_count` without changing raw answers.
- Composite foreign keys prevent cross-session Lock/discovery evidence, mismatched completion Daily, and session content that differs from its Daily. A trigger makes session Daily/content binding immutable.

## Genericization

`ConwayNodeId`, `CONWAY_NODE_IDS`, global max turns, hardcoded required nodes, and hardcoded guidance were removed from generic session/policy contracts. Node IDs come from the validated rubric; thresholds, blocking nodes, max turns, and copy come from SERVER_POLICY. FakeJudge is fixture-aware only through a rubric discriminator and does not own policy or Reveal.

## M3 handoff and limitations

M2 intentionally schedules only the two acceptance-boundary dates carried by the first approved fixture; adding future approved schedules is an editorial seed change, not row-count calculation. Replay UX, accounts/merge, Redis/idempotency/nonce, abuse controls, analytics, adaptive targeting, AI comparison, CMS, and real Judge providers remain future milestones. The FakeJudge recognizes only the approved M2 discriminator.
